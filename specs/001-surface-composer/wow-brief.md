# Wow Brief — UIKit Surface Composer

**Feature:** `001-surface-composer`
**Project:** `examples/surface-composer`
**Role:** Define the moments that make a buyer think “they thought of this too?” and “wait, Telegram Mini Apps can feel like this?”
**Scope:** US1 + US2 full-fidelity wow, with staged hooks for US3–US6.
**Decision:** Wow is created by product agency, tactile response, and system continuity. WebGL is optional later, not the core of the effect.

---

## 1. Strategic wow statement

The demo should not make people say:

> “Nice animation.”

It should make them say:

> “This feels like a real premium product inside Telegram. What else can I touch?”

The wow is not volume. The wow is **evidence of thoughtfulness**.

The target emotional sequence:

```text
premium first impression
→ confident first touch
→ curiosity
→ discovery
→ proof
→ desire to order
```

---

## 2. Desired internal monologue

The experience should trigger these reactions in order:

1. **“This is in Telegram?”**
   The first viewport feels native, contained, and premium.

2. **“It came from one point.”**
   The surface feels generated by a design system, not manually assembled.

3. **“It knows where I touched.”**
   Feedback starts exactly at the contact point.

4. **“They even handled empty space?”**
   Non-actions still acknowledge the user.

5. **“It is the same product, but now it is booking / wallet / support.”**
   US2 shows range without losing continuity.

6. **“The technical proof appeared only when I cared.”**
   The demo respects buyer attention before showing engineering vocabulary.

7. **“This is not a prototype.”**
   Runtime, fallback, reduced motion, and evidence states are honest.

---

## 3. Wow architecture

Use one big signature wow and many small discoverable wows.

```text
Big Wow: Birth from seed
Micro Wow: Every meaningful touch wakes the system
System Wow: One surface remixes across business contexts
Trust Wow: Runtime and fallback states are handled honestly
Proof Wow: The magic opens into real layers after buyer interest
```

### Distribution

| Wow type | Weight | Purpose |
|---|---:|---|
| Birth | 70% | Immediate premium signature |
| Tactility | 15% | Makes user keep touching |
| Continuity remix | 10% | Proves it is a system |
| Proof reveal | 5% | Converts wow into engineering trust |

The big wow must be overbuilt. The rest must be quiet but discoverable.

---

## 4. Hero wow — Birth from seed

### Concept

A single seed condenses into a client-ready Telegram Mini App surface.

The surface is not shown. It is **born**.

### Emotional read

> “The product did not fade in. It assembled itself from rules.”

### Visual sequence

```text
single accent seed
→ safe-area rails emit
→ token grid resolves
→ real UIKit components find their slots
→ one light sweep confirms completion
→ surface breathes once and waits
```

### Why it works

The buyer sees premium craft. The engineer later understands that the motion was mapping system concepts: tokens, safe area, templates, runtime, components.

### Non-negotiables

- No full-screen preloader.
- No generic loader.
- No particle cloud.
- No random 3D object.
- No copy-first reveal.
- No fade-everything-at-once.

---

## 5. Curiosity loop

Every micro-wow should follow this loop:

```text
hint → touch → immediate reaction → small meaning → new affordance
```

Example:

```text
product card has a quiet origin mark
→ user taps product image
→ light appears exactly under finger
→ card identifies media / price / CTA as reusable slots
→ user wonders what happens if they long-press CTA
```

The loop must create curiosity without requiring instructions.

## 6. “They thought of this?” moments

### 6.1 Empty-space recognition

Tapping empty space produces a soft recognition ring and nearby rail glow.

Meaning:

> “The system heard you, but there is no destructive action.”

This is cheap technically and high-value psychologically.

### 6.2 First-touch inspector

The first meaningful touch opens the second layer:

```text
Why it feels premium
UIKit proof appears after the buyer cares
```

The inspector must open from the contact point, not from a generic sheet animation.

### 6.3 Long-press layer split

Long-pressing a rich element splits it into meaning layers:

```text
media
copy
metric
action
trust
runtime
```

It should feel like opening a watch, not breaking glass.

### 6.4 CTA gravity

When the buyer presses `I want this Mini App`, nearby proof and context fragments subtly align toward the CTA.

Meaning:

> “Everything on this surface was leading here.”

### 6.5 Runtime pressure absorption

When keyboard / safe area / theme changes are simulated, the surface should not jump. It should absorb pressure:

- bottom CTA stays clear;
- focused field stays visible;
- theme remaps through semantic tokens;
- status shows native / mock / fallback honestly.

### 6.6 Fallback honesty

When haptic or native share is unavailable, the UI does not pretend. It marks fallback and offers a reversible visual substitute.

Meaning:

> “They even thought about the cases where Telegram capability is missing.”

### 6.7 Focus is premium

Keyboard focus is not a default outline. It is a designed proof path with the same meaning as pointer interaction.

Meaning:

> “Accessibility is part of the craft, not compliance afterthought.”

### 6.8 Loading is construction

Loading state uses rails and skeletons that look like the surface being prepared, not generic shimmer.

Meaning:

> “Even waiting belongs to the system.”

### 6.9 Error is reversible

Error state lowers intensity, marks the affected slot, and gives a next action.

Meaning:

> “The product does not die when something fails.”

## 7. “A tak можно было?” moments

### 7.1 One surface becomes many businesses

The same object becomes shop, booking, wallet, support, and community.

No page reload. No carousel. No screenshots.

The user should feel:

> “This is not one app. This is a repeatable product surface.”

### 7.2 Technical proof appears only after desire

Before the first meaningful touch, there is no token / runtime / recorder / test vocabulary.

After touch, proof appears as a reward, not as a docs page.

### 7.3 Runtime events become visible forces

Safe area, keyboard, theme, native button, and fallback should behave like forces the surface absorbs.

The user should feel:

> “Telegram constraints are not hidden. They are handled.”

### 7.4 Proof receipt is generated from the run

Later scenes should compress the interaction history into a deterministic receipt.

The receipt answers:

- what was remixed;
- what was touched;
- which runtime states were survived;
- what was native / mock / fallback;
- what engineers can inspect next.

## 8. No-WebGL wow strategy

The concern is valid: the referenced sites often use WebGL for spectacle. But this product does not need a 3D world. It needs a living Telegram surface.

WebGL is good for:

- cinematic environments;
- shader identity;
- 3D brand metaphors;
- game-like worlds;
- portfolio proof of rendering craft.

This demo needs:

- touch agency;
- inspectable DOM;
- real UIKit components;
- Telegram-safe performance;
- accessibility;
- deterministic visual snapshots;
- reduced-motion parity;
- proof that the UIKit did the work.

So the no-WebGL wow should come from **screen-space precision**:

| WebGL-like impression | No-WebGL execution |
|---|---|
| Depth | CSS perspective + shadow layers |
| Glow | radial-gradient masks |
| Shader pulse | pseudo-element with CSS variables |
| 3D orbit | FLIP + `rotateY` on DOM slots |
| Particle energy | banned; use rails and one light sweep |
| Object physics | transform-based pressure response |
| World continuity | persistent origin and shared slots |

The buyer should not think “that is a 3D renderer”. They should think “the Mini App itself is alive”.

---

## 9. Optional WebGL rule

WebGL may enter later only if all three are true:

1. The live UIKit surface remains DOM, accessible, and testable.
2. WebGL is stage-only or background-only, never the source of product truth.
3. The same experience passes without WebGL.

Allowed later:

- low-intensity stage depth;
- atmospheric background light;
- non-interactive phone shadow/reflection.

Not allowed:

- WebGL-rendered UI controls;
- shader-only state changes;
- invisible DOM duplicates pretending to be the product;
- performance that breaks Telegram WebView confidence.

## 11. Anti-wow

Banned because it makes the product look cheaper:

- perpetual shimmer;
- particles;
- full-screen gradient fog;
- generic bouncy spring;
- page cross-fade;
- layout-property animation;
- hover-only secrets;
- technical labels before first touch;
- random decorative 3D object;
- confetti after CTA;
- fake native haptics;
- evidence pins claiming passed without fixtures.

## 12. Pass tests

### 12.1 Lean-in test

Hide all copy. The viewer should still lean in during birth.

Question:

> “Does it look like a system generated a live product?”

### 12.2 Curiosity test

Give the demo to a reviewer with no instructions.

Pass condition:

- they tap at least five things;
- each tap gives visible feedback;
- they discover at least one non-obvious response;
- they do not get lost.

### 12.3 Buyer-first test

Before first meaningful touch:

- no token vocabulary;
- no runtime vocabulary;
- no recorder vocabulary;
- no test vocabulary;
- one primary action only.

### 12.4 Engineer-trust test

After first meaningful touch:

- proof layer maps to real visible UI;
- runtime status is honest;
- fallback is not disguised as native;
- reduced motion is meaningful;
- recorder events match visible effects.

### 12.5 WebGL necessity test

Ask:

> “Would WebGL communicate something the UIKit itself cannot communicate?”

If the answer is “it would look cooler”, do not add it.

If the answer is “the stage needs atmospheric depth, while the product remains DOM”, consider it later.

---

## 13. Final wow sentence

The demo wins when the buyer thinks:

> “I opened a Telegram Mini App, touched a product surface, and it behaved like a premium native system. I want this for my business.”

The engineer should then think:

> “The magic is constrained, testable, and built from the UIKit. I can trust this.”
