# Feature Specification: UIKit Surface Composer

**Feature Branch**: `001-surface-composer`

**Created**: 2026-06-16

**Status**: Draft

**Input**: Migrated from `plans.md` (the living ExecPlan). Full intended vision is
the source of truth. The earlier partial implementation was removed from
`examples/trailhead`; the work is a fresh build in `examples/surface-composer`,
and the gap between this spec and that fresh build is what remains to build.

## Overview

Surface Composer is an interactive demo that runs inside a Telegram Mini App
WebView and sells the reusable `tg-mini-app-uikit` to two audiences in one run:
founders/buyers who must feel premium craft first, and engineers who must then
trust the system behind it. It is a single continuous instrument — one origin
point that generates a Telegram-native surface, remixes it across business
contexts, exposes interaction trust, survives Telegram runtime pressure, opens
into build proof, and compresses into a shareable receipt. It is not a tabbed
app, a component gallery, or a landing page. The live surface is inspectable DOM
(no-WebGL by default): its premium, alive feel comes from product agency — the
surface itself recognizing touch, absorbing runtime pressure, and remixing in
place — not from a separate renderer.

## Clarifications

### Session 2026-06-16

- Q: How does the buyer move between the six scenes? → A: Linear — a single
  primary action advances scene-by-scene in a fixed keynote order (no
  tabbar/navbar/free jumping); the origin point is the continuity object.
- Q: Which runtime environment must this iteration target? → A: Browser-simulated
  Telegram context for this first phase; real-Telegram execution (native
  MainButton/haptic/theme actually firing, deployed in the client) is deferred to
  a later phase.
- Q: Which user stories are in scope for the first delivered increment? → A: US1
  (first launch) and US2 (range) at full fidelity; US3–US6 remain specified but
  deferred to a later increment.
- Q: What is the "done" bar for the premium feel / motion? → A: State + recorder +
  reduced-motion + no-overlap assertions, PLUS visual snapshots at key motion
  states and a performance budget (no long task > 50 ms, 60fps target).
- Q: Does the first increment use WebGL/3D to create the wow? → A: No. The live
  UIKit surface is inspectable DOM rendered with CSS, SVG, and a small rAF layer;
  the "alive" feel comes from product agency (the surface itself responding), not a
  separate renderer. WebGL is allowed later only as a non-interactive
  stage/background atmospheric layer that never renders product UI and never holds
  product state, and the full experience MUST pass with WebGL absent.
- Q: What is the full motion-state vocabulary the surface must expose on the DOM? →
  A: US1 `seed → rails → assembling → light-sweep → idle → first-touch →
  inspector-open`; US2 `remix-start → separating → rotating → recomposing → locked →
  continuity`; cross-cutting `browser-fallback`, `theme-shift`, `safe-area-pressure`,
  `keyboard-pressure`, `native-mirror`, `permission-denied`, `reduced-motion` — each
  surfaced via `data-scene` / `data-motion-state` / `data-runtime-mode` /
  `data-business-context` (and the dedicated `data-reduced-motion` hook from
  constitution Principle IV) so every state is snapshot-addressable.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - First launch sells a Mini App outcome (Priority: P1)

A non-technical founder opens the demo on a phone-sized surface during a client
call. In the first seconds they understand: this runs inside Telegram, it looks
premium and alive, it could become their shop/booking/wallet/support, and the
first desired action is to order it. No token, runtime, or test vocabulary is
visible yet. The surface visibly assembles from a single origin point so it
reads as generated by a system, not a static mockup. Only after a meaningful
touch does a second layer reveal that UIKit proof exists.

**Why this priority**: This is the whole sale. If the first viewport does not
make a buyer want the Mini App, nothing downstream matters. It is the MVP slice:
shippable and valuable on its own.

**Independent Test**: Open the default path and confirm buyer-first promise,
business switcher, and a single primary commitment action are present and
readable, with no technical-first vocabulary, before any interaction.

**Acceptance Scenarios**:

1. **Given** the demo opens at the default path, **When** the first viewport
   settles, **Then** the buyer promise ("open, trust, order" intent), a business
   switcher (the four primary contexts shop / booking / wallet / support; community
   is reachable through the US2 remix per FR-004), a live premium surface, and one
   primary "order this Mini App" action are visible without overlap.
2. **Given** the first viewport, **When** the buyer reads it, **Then** no token,
   runtime, recorder, or test language is visible, and the secondary build-proof
   affordance is absent.
3. **Given** the buyer makes a first meaningful touch on the live surface,
   **When** the touch is recognized, **Then** a second-layer inspector opens from
   the contact point (state `inspector-open`) surfacing at least one named UIKit
   proof element (component / state / token / accessibility / runtime), and the
   build-proof affordance becomes available. (The "why it feels premium" framing
   lives in the inspector copy, not as a testable assertion.)
4. **Given** the first viewport, **When** the buyer presses the primary action,
   **Then** nearby proof and context fragments subtly align toward it (CTA gravity,
   transform/opacity only — no confetti) so the surface reads as "everything led
   here", and a recorder event is emitted.
5. **Given** empty space inside the surface, **When** it is tapped, **Then** a soft
   recognition ring appears at the contact point and nearby rails barely glow with
   no state change (recognized, not destructive).
6. **Given** reduced motion is preferred, **When** the surface loads, **Then**
   the origin/assembly is shown as static state with no looping motion, and all
   meaning is preserved.

### User Story 2 - One surface speaks many businesses (Priority: P2)

The same Telegram-native surface remixes between commerce, booking, wallet,
support, and community contexts. The buyer sees that this is a fast product
surface for Telegram distribution, not one fixed screen, and that the kit makes
producing multiple client scenarios repeatable instead of hand-coded.

**Why this priority**: Proves range and reusability — the core "it's a system"
argument — directly after the buyer is hooked.

**Independent Test**: Trigger the remix and confirm the business context changes
in the expected order while token, safe-area, theme, and runtime continuity is
preserved and the surface stays Telegram-sized.

**Acceptance Scenarios**:

1. **Given** the live surface in one context, **When** the buyer remixes it,
   **Then** the slots separate, rotate around the seed axis, and recompose
   (`remix-start → separating → rotating → recomposing → locked`) so the business
   context changes to the next in the defined order and the primary action updates
   without layout shift or page reset.
2. **Given** any remix, **When** the new context settles, **Then** design tokens,
   safe-area bounds, theme, selected context, and runtime status remain anchored
   (continuity is visible, not reset).
3. **Given** the surface across all contexts, **When** measured at 320 / 375 /
   430 px and desktop preview, **Then** there is no text overflow, no overlapping
   controls, and the shell stays a centered TMA surface, not a desktop dashboard.
4. **Given** reduced motion, **When** remixing, **Then** rotation is replaced by a
   stepped crossfade and continuity marks remain, with identical recorder events.

---

### User Story 3 - Every interaction builds trust (Priority: P2)

Every tap, hover, long press, focus, loading, haptic response, and unsupported
fallback feels like part of the kit's contract, not custom animation glue. A
touch reveals the reason behind the feel (component, state, token, accessibility
contract, runtime/haptic status). Empty space responds with "recognized, no
action" instead of feeling dead. Rich elements can split into meaning layers on
long press without looking randomly shattered.

**Why this priority**: Conversion in a cramped WebView depends on instant,
consistent, accessible confidence. This is what separates "real" from "cheap".

**Independent Test**: Exercise each interaction probe (pointer and keyboard) and
confirm each produces a visible, meaningful reaction plus a recorder event with
honest native/mock/fallback status.

**Acceptance Scenarios**:

1. **Given** any primary interactive target, **When** the buyer taps it, **Then**
   there is an immediate purposeful response and a recorder event naming source,
   target, state, visible reaction, and native/mock/fallback status.
2. **Given** a haptic-capable action, **When** triggered without native haptics,
   **Then** the fallback is explicit and no fake device vibration is claimed.
3. **Given** keyboard navigation, **When** a target is focused and activated,
   **Then** it exposes the same proof path as pointer interaction, with a visible
   unclipped focus ring.
4. **Given** empty space, **When** tapped, **Then** the demo signals recognition
   without a destructive action.

---

### User Story 4 - Native under Telegram runtime pressure (Priority: P2)

The surface still feels native when Telegram changes: keyboard rises, safe areas
squeeze, viewport height changes, native chrome toggles, BackButton takes
priority, MainButton mirrors honestly, theme changes flow through tokens, and
permission denial degrades reversibly. Runtime events are shown as forces the
kit absorbs without panic, jump, or arbitrary resize.

**Why this priority**: This is why a Telegram-specific kit exists. Ordinary web
UI breaks under this pressure; proving the kit does not is a core differentiator.

**Independent Test**: Inject each runtime stressor from deterministic fixtures
and confirm a visible settled state plus a recorder event with an honest runtime
source for every one.

**Acceptance Scenarios**:

1. **Given** the keyboard opens, **When** the viewport changes, **Then** the
   bottom action and focused field stay visible and clear of the home indicator,
   with no content jump after the first settled frame.
2. **Given** a theme change, **When** it arrives, **Then** background, card, text,
   muted, accent, separator, and state colors remap through semantic tokens (not a
   raw color-only toggle).
3. **Given** an overlay is open, **When** Back is pressed, **Then** the overlay
   closes before any navigation.
4. **Given** the demo runs outside native Telegram (browser preview/SSR), **When**
   a native capability is unavailable, **Then** the fallback state is shown and
   visually distinct from native, never presented as native.

---

### User Story 5 - Build proof for engineers (Priority: P3)

After the founder is hooked, the team sees the magic is maintainable: the active
surface opens into real build layers (tokens, atoms, composites, templates,
Telegram runtime hooks, accessibility contracts, Storybook evidence, tests,
recorder evidence). Evidence pins attach to real visible UI elements rather than
forming a docs page, and every claim is fixture-backed and honest.

**Why this priority**: Converts wow into engineering trust and reduces the cost
of future scenarios. Important, but only after the buyer-facing value lands.

**Independent Test**: Open the build-proof scene and confirm each layer and pin
maps to a fixture item, with missing evidence labelled `candidate`/`planned`,
never `passed`.

**Acceptance Scenarios**:

1. **Given** the active surface, **When** build proof is opened, **Then** layers
   can be isolated and recomposed back into the live surface, reachable by
   keyboard, with Escape closing the lattice first.
2. **Given** any evidence pin, **When** displayed, **Then** it maps to a real
   fixture item, and unproven items read as `candidate`/`planned`.
3. **Given** 320 px and RTL with long localized labels, **When** proof is shown,
   **Then** there is no text overlap and no unreadable pins.

---

### User Story 6 - Shareable proof / handoff (Priority: P3)

The run compresses into a share-ready receipt that answers "what do I send the
person with budget?" and "what do engineers use next?" without leaving the TMA.
It is a receipt generated from recorder data (templates remixed, interactions
tested, runtime events survived, accessibility/reduced-motion covered, fallback
identified, layers exposed), plus a deterministic replay of milestones.

**Why this priority**: Closes the loop into distribution (Telegram chats,
channels, client handoff). Valuable, but depends on the prior scenes existing.

**Independent Test**: Generate the proof from a fixed fixture and confirm an
identical fixture yields an identical proof hash and visual state, with native
and fallback share branches both testable.

**Acceptance Scenarios**:

1. **Given** a completed run, **When** the proof capsule is generated, **Then** it
   is built from recorder fixture data and an identical fixture produces an
   identical proof hash and visual state.
2. **Given** a missing native capability, **When** the receipt is shown, **Then**
   it is reported as fallback, not passed.
3. **Given** the replay ribbon, **When** a milestone is selected, **Then** the
   scene state is restored deterministically; pause/resume does not mutate proof
   data.
4. **Given** native share is unavailable, **When** the buyer shares, **Then** an
   inline fallback (copy/replay) is offered without claiming native share.

### Edge Cases

- Reduced motion: every scene has a static path preserving all meaning; no scene
  depends on rotation, depth, refraction, or long-path travel to be understood.
- Non-Telegram runtime (browser/SSR): all native-only capabilities degrade to a
  clearly-labelled fallback.
- Narrow width (320 px) and RTL with long localized labels: no overlap, no
  overflow, no unreadable proof.
- Rapid repeated taps: the surface must not get stuck in an entering/active state
  and must settle within the motion budget.
- Missing/denied native capability (haptic, share, permission): reversible
  blocked state, never dead UI or a false success.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The demo MUST run as a single continuous Telegram Mini App surface
  in its own example app (`examples/surface-composer`) whose default launch path
  presents the buyer-first first impression; the separate `examples/trailhead`
  example MUST NOT be modified.
- **FR-002**: The first viewport MUST lead with buyer-facing value and MUST NOT
  display token, runtime, recorder, or test vocabulary, nor the build-proof
  affordance, before a meaningful interaction.
- **FR-003**: The surface MUST visibly assemble from a single origin point through
  one signature reveal (staggered resolution, not a uniform fade) that closes with a
  single committed light sweep; afterward only the surface breathes once and settles
  to rest (`idle`, scale ~1.004) while text, icons, and cards stay static (no
  perpetual shimmer), so that with copy hidden the motion alone reads as
  system-generated rather than a static mockup.
- **FR-004**: Users MUST be able to remix the same surface across at least shop,
  booking, wallet, support, and community contexts while token, safe-area, theme,
  selected context, and runtime continuity are preserved; the change MUST morph the
  same surface (shared elements persist) rather than cross-fade between separate pages.
- **FR-005**: Every visible effect MUST produce a recorder event capturing source,
  target, visible reaction, native/mock/fallback status, and the active scene and
  motion state (plus business context for remix events), so recorder events carry the
  same state vocabulary exposed on the DOM (FR-019).
- **FR-006**: Every primary interactive target MUST have a purposeful response to
  pointer and keyboard input, and empty space MUST acknowledge recognition without
  a destructive action.
- **FR-007**: The demo MUST present Telegram runtime events (keyboard, safe area,
  viewport, native chrome, BackButton, MainButton, haptic, theme change,
  permission denial, browser fallback) as absorbed forces with honest runtime
  source labelling.
- **FR-008**: The demo MUST reveal UIKit build layers and evidence pins that are
  fixture-backed, labelling unproven evidence as `candidate`/`planned`, never
  `passed`.
- **FR-009**: The demo MUST produce a deterministic, shareable proof receipt and a
  replay of milestones; identical fixtures MUST yield identical proof output.
- **FR-010**: Every scene MUST provide a reduced-motion path that preserves all
  meaning and emits the same recorder events as the full-motion path.
- **FR-011**: All interactive regions MUST have accessible names and visible focus;
  Back/Escape MUST close overlays before navigating; color MUST NOT be the only
  state signal.
- **FR-012**: The demo MUST be composed from existing public UIKit exports plus
  demo-only helpers under `examples/`; it MUST NOT add new public UIKit exports.
- **FR-013**: Motion MUST be limited to transform, opacity, isolated clip/mask, and
  semantic CSS-variable interpolation; layout-property animation (width, height,
  top, left, margin, padding) is prohibited.
- **FR-014**: Native, mock, and browser-fallback states MUST be visually distinct,
  and no native capability MAY be claimed when only a fallback exists.
- **FR-015**: Buyers MUST advance through the six scenes via a single primary
  action that moves scene-by-scene in a fixed keynote order; tabbar/navbar and
  free jumping between scenes are out of scope, and the origin point MUST carry
  across scenes as the continuity object.
- **FR-016**: Signature motion sequences MUST stay within a performance budget (no
  long task > 50 ms; 60fps target) on the reference preview, and key motion states
  MUST have visual-snapshot coverage acting as a regression gate.
- **FR-017**: Every primary touch MUST produce visual feedback within 100 ms anchored
  at the contact point (empty-space acknowledgement is owned by FR-006).
- **FR-018**: The live UIKit surface MUST be inspectable, accessible DOM rendered
  with CSS, SVG, and a small rAF layer; WebGL/3D MUST NOT render product UI or hold
  any product state in this increment, and the full experience MUST pass with WebGL
  absent. (Stage-only atmospheric WebGL is a possible later phase — see Assumptions.)
- **FR-019**: The surface MUST expose its motion and runtime state on the DOM via the
  constitution's deterministic hooks — `data-scene`, `data-motion-state`,
  `data-runtime-mode`, `data-business-context`, and `data-reduced-motion` — covering
  US1 (`seed`, `rails`, `assembling`, `light-sweep`, `idle`, `first-touch`,
  `inspector-open`), US2 (`remix-start`, `separating`, `rotating`, `recomposing`,
  `locked`, `continuity`), and cross-cutting runtime states (`browser-fallback`,
  `theme-shift`, `safe-area-pressure`, `keyboard-pressure`, `native-mirror`,
  `permission-denied`), with reduced motion exposed through the dedicated
  `data-reduced-motion` hook, so every state is snapshot-addressable rather than
  timing-dependent.
- **FR-020**: Discoverable microinteractions MUST follow a curiosity loop (hint →
  touch → reaction within the FR-017 feedback budget → small meaning → new
  affordance), and the primary action MUST exhibit gravity — on press, the proof and
  context fragments within the first viewport align toward it using transform/opacity
  only — so the surface invites further touch without instructions. Under reduced
  motion, gravity resolves to a static aligned state and empty-space recognition to a
  static highlight, both emitting the same recorder events (FR-010).
- **FR-021**: Decorative wow patterns are prohibited: perpetual shimmer, particle
  fields, full-screen gradient fog, generic spring bounce, page cross-fade between
  contexts, confetti after the CTA, hover-only secrets, and any decorative 3D object;
  loading MUST read as construction rails, not generic shimmer.

### Key Entities

- **Surface**: the live Telegram-native composition shown in the center; carries a
  business context, design tokens, safe-area bounds, theme, and runtime status.
- **Business context**: a buyer-recognizable scenario the surface remixes into
  (shop, booking, wallet, support, community).
- **Recorder event**: a logged interaction/runtime occurrence with source, target,
  visible reaction, native/mock/fallback status, active scene, motion state, and
  (for remix) business context.
- **Build layer / evidence pin**: a fixture-backed proof element (token, component,
  Storybook, test, a11y, runtime, recorder) attached to a real UI element.
- **Proof receipt**: the deterministic, shareable summary generated from recorder
  data, including a reproducible proof hash and milestone replay.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Within 10 seconds of opening, a reviewer can state that the demo
  sells a reusable kit, not one custom app.
- **SC-002**: 100% of the first-viewport visible copy is buyer-facing; 0 token /
  runtime / recorder / test terms appear before a meaningful interaction.
- **SC-003**: A developer can identify at least five distinct UIKit primitives in
  use during the first scene.
- **SC-004**: At least five microinteractions are discoverable without
  instructions, each with a visible response.
- **SC-005**: 100% of triggered visible effects produce a corresponding recorder
  event with an honest native/mock/fallback status.
- **SC-006**: No overlap or overflow occurs at 320 / 375 / 430 px, desktop
  preview, and RTL, across all scenes.
- **SC-007**: Every scene is fully understandable under reduced motion, with no
  meaning lost and identical recorder events.
- **SC-008**: 100% of runtime stressors produce a visible settled state and a
  recorder event labelled native, mock, or fallback honestly.
- **SC-009**: 0 evidence pins, layers, or proof fields claim `passed` without a
  backing fixture; identical fixtures produce an identical proof hash.
- **SC-010**: The Surface Composer e2e suite and the project quality gates pass
  from a clean worktree, and the existing Trailhead e2e suite stays green.
- **SC-011**: Every in-scope scene has visual-snapshot coverage at its key motion
  states — US1 `seed`, `rails`, `assembling`, `idle`, `first-touch`, `inspector-open`;
  US2 `remix-start`, `separating`, `rotating`, `locked`, plus the reduced-motion remix
  substitute — and the snapshot gate detects an unintended visual regression. Transient
  in-between frames (`light-sweep`, `recomposing`, `continuity`) are intentionally
  excluded as transition states, not key frames.
- **SC-012**: Signature motion sequences complete with no long task > 50 ms and no
  sustained frame-budget breach (60fps target) on the reference preview.
- **SC-013**: With all surface copy hidden, in a moderated test a majority of
  reviewers state, from motion alone, that (1) a system generated the surface, (2) the
  origin point matters, (3) the surface responds to touch, (4) the same object becomes
  different businesses (mechanically corroborated by `data-business-context` changing
  during the copy-hidden remix), and (5) Telegram constraints are absorbed (evidenced
  in-scope by the safe-area rails emitted during birth) — the motion-without-copy /
  animation-acceptance test.
- **SC-014**: First visual feedback for any primary touch occurs within 100 ms; no
  primary target reads as unresponsive.
- **SC-015**: The live surface is inspectable DOM — every surface element and proof
  pin resolves in the DOM/accessibility tree — and the full in-scope experience
  passes with WebGL/3D entirely absent (no-WebGL gate).

## Assumptions

- The audience is split: founders/buyers feel polish first, engineers trust the
  system second; the demo must serve both without one defeating the other.
- The demo is demo-only and lives in its own example app
  `examples/surface-composer`; it reuses existing UIKit exports and the existing
  Telegram runtime adapter without new public API, and does not modify the
  separate Trailhead example.
- Telegram context is simulated in-app (launch context, native chrome, safe-area,
  runtime events, theme variables); the demo does not depend on real Telegram
  dialogs, an external chat scene, or a video sequence. This first phase targets
  the browser-simulated environment; real-Telegram execution (native
  MainButton/haptic/theme actually firing, deployed in the client) is deferred to
  a later phase, while honest native/mock/fallback labelling is still required now.
- First delivered increment scope: US1 (first launch) and US2 (range) brought to
  full fidelity. US3–US6 remain part of this spec but are deferred to a later
  increment. The earlier partial first pass (a compact interactive loop) was
  removed from `examples/trailhead`; this increment is a fresh build in
  `examples/surface-composer` toward full US1/US2 fidelity, driven by
  `/speckit.plan` and `/speckit.tasks`.
- The first increment is no-WebGL by default: the wow comes from product agency (the
  DOM surface recognizing touch, absorbing runtime pressure, and remixing in place),
  not a separate renderer. The motion grammar, wow distribution (Birth ~70% /
  Tactility ~15% / Continuity ~10% / Proof ~5%), no-WebGL implementation strategy, and
  full state model are fixed by the companion `animation-brief.md` and `wow-brief.md`
  in this folder. WebGL is out of scope now and allowed later only as a stage-only
  atmospheric layer (the live surface stays DOM, accessible, and testable).
- `plans.md` and `trailhead-demo.plan.md` are historical design input; this spec, the
  constitution, and the confirmed `design-brief.md` / `animation-brief.md` /
  `wow-brief.md` companions are the authority.
